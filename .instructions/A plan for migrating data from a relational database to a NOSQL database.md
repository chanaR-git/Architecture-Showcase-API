# מסמך ארכיטקטורה: העברת מסד הנתונים ל-NoSQL (MongoDB)
## פרויקט: Chinece Sale DB (מכירה פומבית סינית)

מסמך זה מתאר את תוכנית המעבר ממסד הנתונים הרלציוני הקיים (SQL Server) למסד נתונים מוכוון מסמכים (MongoDB), תוך שימוש בעקרונות דניורמליזציה, שיפור ביצועי השליפות והתאמה להנחיות הפרויקט.

---

## 1. אסטרטגיית מידול וקשרים (Data Modeling Strategy)

במעבר ל-NoSQL, המטרה המרכזית היא לצמצם את הצורך בפעולות JOIN מורכבות ויקרות בזמן ריצה, ולנצל את מבנה המסמכים הגמיש. בחרנו בשתי שיטות מרכזיות לניהול הקשרים:

### א. הטבעה (Embedding)
שיטה זו נבחרה עבור ישויות שהן בעלות קשר הדוק, תלויות לחלוטין בישות האם, או עבור נתונים קטנים וסטטיים יחסית:
* קטגוריות (Categories -> gifts): שם הקטגוריה מוטמע ישירות בתוך מסמך המתנה. אין צורך באוסף נפרד כיוון ששם הקטגוריה הוא שדה טקסטואלי פשוט לסינון.
* סל קניות (Baskets -> users): סל הקניות הוא ישות דינמית וזמנית השייכת באופן בלעדי למשתמש בודד. הוא מיוצג כמערך פנימי בתוך מסמך המשתמש.

### ב. קישור (Referencing)
שיטה זו נבחרה עבור ישויות עצמאיות, או כאשר ישנה ישות אחת המקושרת לישויות רבות (קשר של One-to-Many) ונרצה למנוע כפילות ועדכוני ענק במקרה של שינוי נתונים:
* תורמים (Donors -> gifts): תורם אחד יכול לתרום מתנות רבות. באוסף המתנות נשמור מזהה (donorId) המקשר לאוסף התורמים הייעודי.
* רכישות (Purchases): כדי למנוע את התנפחות מסמך המשתמש לאורך זמן (כאשר משתמש רוכש מאות כרטיסים), הרכישות מנוהלות באוסף נפרד המקשר בין המשתמש (customerId) לבין המתנה (giftId).
* הזוכה במתנה (winnerId -> users): שדה בתוך המתנה המכיל רפרנס למזהה המשתמש שזכה בהגרלה.

## 2. מבנה האוספים ומסמכי ה-JSON (Collections & Schema)

להלן מבנה ה-JSON המדויק עבור ארבעת האוספים המרכזיים שיוקמו במסד הנתונים:

### א. אוסף משתמשים (users)
מכיל את פרטי המשתמש, תפקידו במערכת, ואת סל הקניות הנוכחי שלו (מוטמע כמערך).

{
  "_id": 1,
  "name": "ישראל ישראלי",
  "password": "hashed_password_string_here",
  "email": "israel@example.com",
  "phone": "050-1234567",
  "role": 0,
  "basket": [
    {
      "giftId": 101,
      "amount": 3
    },
    {
      "giftId": 102,
      "amount": 1
    }
  ]
}

### ב. אוסף מתנות (gifts)
מכיל את פרטי הפרס, מחיר הכרטיס, תמונת המוצר, הטבעה של הקטגוריה, וקישורים לתורם ולזוכה המאושר.

{
  "_id": 101,
  "name": "חופשה משפחתית מפנקת",
  "description": "סוף שבוע זוגי + 2 ילדים במלון חמישה כוכבים בצפון כולל ארוחות",
  "price": 50,
  "imagePath": "/images/gifts/vacation_north.jpg",
  "category": "נופש ופנאי",
  "donorId": 5,
  "winnerId": null
}

### ג. אוסף תורמים (donors)
אוסף עצמאי השומר את פרטי הקשר של התורמים העסקיים או הפרטיים של המערכת.

{
  "_id": 5,
  "name": "רהיטי איכות בעמ",
  "email": "info@luxuryfurniture.co.il",
  "phone": "03-9876543"
}

### ד. אוסף רכישות (purchases)
מתעד כל רכישת כרטיס שנרכשה בפועל, ומקשר בין הלקוח למתנה עם חותמת זמן מדויקת.

{
  "_id": 5001,
  "customerId": 1,
  "giftId": 101,
  "purchDate": {
    "$date": "2026-06-25T17:28:00Z"
  }
}

## 3. מיפוי קשרים ומפתחות (SQL to NoSQL Mapping)

| טבלה מקורית ב-SQL | אוסף יעד ב-MongoDB | סוג הקשר והערות ארכיטקטוניות |
| :--- | :--- | :--- |
| Users | users | ישות עצמאית. מכילה כעת גם את נתוני ה-Basket. |
| Baskets | הוטמעה בתוך users | הפכה למערך פנימי בשם basket כדי לייעל שליפת עגלה למשתמש מחובר. |
| Categories | הוטמעה בתוך gifts | השדה Name נשמר ישירות בתוך המתנה כשדה טקסט פשוט (category). |
| Donors | donors | ישות עצמאית. מקושרת ל-gifts דרך donorId (קשר 1 ל-Many). |
| Gifts | gifts | ישות עצמאית. מחזיקה winnerId כרפרנס אופציונלי ל-users. |
| Purchases | purchases | אוסף קישור עצמאי (Reference) המקשר בין משתמשים למתנות שרכשו. |
